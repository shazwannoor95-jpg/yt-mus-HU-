# Google sign-in in YTM Head Unit

## Account verification in 0.4.5

The screenshot showing “YouTube could not verify your sign-in” came from the account check after the WebView returned. That message covered request errors and missing account headers, so the exact cause on the head unit is unknown. The Android source also exposed two session parsing gaps. It expected a quoted `SESSION_INDEX` and only recognized the lowercase `datasyncId` spelling.

YTM now carries the selected account context from the current YouTube Music page. It reads only four configuration fields from the first-party page, with a bounded wait and a fallback to the page's account index or YouTube Music's landing-page configuration. The context is tied to the existing app session in memory and cleared on sign-out. No external browser session is accessed.

The account check uses the existing account menu. If the menu lacks an account header, it accepts an explicit signed-in status or checks for that status on the signed-in Home request. A signed-out response, HTTP rejection or response without positive sign-in evidence cannot mark the account verified.

Settings › Account now distinguishes HTTP refusal, expired or rejected sessions, timeouts, DNS and TLS failures, and unrecognized responses. It can retry a recoverable check with the current session. Its **Copy diagnostic** action includes a fixed verification code and excludes response bodies, account identifiers and session data.

The implementation was compared with upstream `ytm-rs` signed-in request context and account response detection, and Metrolist's WebView context handoff. REA and Craft Anything inspected the Windows installer and compared the Android packages. [ytm-rs account verification](https://github.com/grapedjuice/ytm-rs/blob/99d404b9d78d0edb72361eb8c5c465ae6af57979/src/ytmapi.rs) · [Metrolist login screen](https://github.com/MetrolistGroup/Metrolist/blob/main/androidApp/src/main/kotlin/com/metrolist/android/ui/screens/LoginScreen.kt)

Gradle built 0.4.5 and all 17 tests passed, including 15 API 31 fixture tests. The release uses the v0.4.4 signing certificate and contains identical resources and assets. The workspace proxy blocked the Google and YouTube Music endpoints, so live account verification still needs a device test.

## What failed in 0.4.3

The diagnostic was generated by the `WebViewClient.shouldOverrideUrlLoading` callback in `my.ytmhu.GoogleSignIn.show`. For a main-frame HTTPS URL, `trustedLoginPage` had to approve the exact origin and, on general-purpose domains, an authentication path. When that check returned false, the client consumed the navigation. A continuation was only considered for `intent:` URLs, so the HTTPS request produced “unrecognized secure site” and “no in-app continuation.” The old diagnostic reduced the hostname to its last two labels. It confirms the code path but leaves the exact hostname unverified. [0.4.3 implementation](https://github.com/shazwannoor95-jpg/yt-mus-HU-/blob/6de61277f015832a8a56a6ff40ec197e57d0b862/app/src/main/java/my/ytmhu/GoogleSignIn.java#L245)

## What 0.4.4 does

- Accepts specific Google account hosts on `google.com.my` and the referenced `accounts.google.co.uk` origin. The Malaysian apex, `www` and support hosts are limited to their respective authentication paths. Similar domains, other `.com.my` sites, user-info, nonstandard ports and insecure schemes are rejected. Chromium's Google TLD list confirms the regional base domains. [Chromium Google TLD list](https://github.com/chromium/chromium/blob/main/components/google/core/common/google_tld_list.h)
- Sends account selection to Google's AccountChooser and leaves verification inside the provider's flow. Offers Back, Restart and a validated first-party HTTPS fallback when an Android intent supplies one. TLS errors cancel loading. A blocked or failed page cannot finish login. The sign-in dialog can be closed without invoking account verification.
- Opens the fixed YouTube Music URL with a system HTTPS intent when the user chooses **Open separately**, including when WebView is unavailable. It works with compatible browsers or apps, irrespective of Chrome and Play Services availability. That browser or app has its own session. A Play Services-dependent challenge or one unsupported by the installed WebView can still require Google's alternative verification method.
- Copies the validated hostname, redirect scheme, Android and WebView versions, browser and Play Services availability, the authentication mechanism, a fixed result message and a sanitized error category or numeric code. URL paths, query strings, fragments, credentials, cookies, OTPs and tokens are excluded.

## Architecture and alternatives

YTM's dedicated WebView completes a **YouTube Music web session**. The existing native client uses that app-owned session against YouTube Music's InnerTube web endpoints. The WebView store remains local to this app, and successful account verification still requires a return to the HTTPS YouTube Music origin and an account check. This release adds no session import from Chrome, other browsers or other apps.

AppAuth implements browser-based OAuth with PKCE and a registered redirect handler. Google Credential Manager provides credentials such as an ID token for an app's identity provider configuration. The public YouTube Data API consumes OAuth scopes for its own endpoints. These grants cannot create the YouTube Music web session used for the personalized home feed, playback and library in this app. A separate integration could use OAuth for the public playlist and channel APIs with a registered client, verified callback and explicit consent. The official YouTube Music app or website is the browser-based option for the full account experience. [AppAuth](https://github.com/openid/AppAuth-Android) · [Android identity samples](https://github.com/android/identity-samples) · [YouTube Data API authentication](https://developers.google.com/youtube/data/guides/authentication) · [Google's YouTube Data API discovery schema](https://github.com/googleapis/google-api-go-client/blob/main/youtube/v3/youtube-api.json)

## Build and verification

With JDK 17, Gradle 8.11.1, Android SDK 35 and Build Tools 35, run `gradle :app:testDebugUnitTest :app:assembleDebug`. Gradle writes the APK to `app/build/outputs/apk/debug/app-debug.apk`. When present, the existing `build/debug.keystore` is used so the APK can update the previous test build.

The Gradle tests cover redirect handling, selected-account context, cancellation, the app session across dialog recreation, account response fixtures, sanitized diagnostics, queue and Now Playing controls, artwork sizing and the compact landscape mini player. The Android fixture tests run at API 31. APK signature verification runs with API 27 as the minimum.

REA and Craft Anything inspected the supplied Windows installer and the Android APKs. The Windows file is an Inno Setup wrapper, so the upstream Rust source provided the mini-player, artwork sizing and login behavior for comparison. APK archive comparison and byte checks confirmed the upstream theme, font and artwork assets were preserved. The Android frosted effect uses a blurred album sample and a tint gradient. It renders inside the Android app with the mini player.

Live sign-in, account selection, two-factor prompts, on-device WebView persistence, stream playback and visual checks still require a physical Android device or suitable emulator and, where relevant, a Google account. `agent-browser` 0.45.0 passed a local navigation smoke test. The workspace proxy blocked access to Google Accounts.
